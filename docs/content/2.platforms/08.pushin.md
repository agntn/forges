## Read a Pushin.eu repository

```ts
import { createProvider, resolveToken } from "@agntn/forges";

const pushin = await createProvider("pushin", resolveToken("pushin") ? {} : { token: "" });

const repo = { owner: "pjullrich", repo: "pushin" };
const tracker = await pushin.repos.get(repo);
const issues = await pushin.issues.list(repo, { state: "all" });
const comments = await pushin.issues.listComments({ ...repo, number: 68 });
```

Got a login? The snippet uses it. Otherwise, public reads go anonymous, writes still need a token.

The API is GitHub shaped, with fewer rooms. So most of this page is about the rooms that aren't there.

The default API base is `https://pushin.eu/api/v1`. forges adds `/api/v1` when missing. For a self hosted instance, pass its bare root as `baseURL`. The MCP server and Pi/OMP extensions use `FORGES_PUSHIN_BASE_URL`.

IDs are strings, such as `repo_033njmWmzIFsMhzbVEe4Kh` and `iss_0350XjM9mMevqk8sUGfTkU`. Issue and pull request numbers stay numbers. Lists page with a `Link` header, like GitHub. forges returns the next page as `nextCursor`.

Cloning? `cloneUrl` points to `git.pushin.eu`, not `pushin.eu`. The code has a different front door. Pi and OMP recognize HTTPS remotes on both hosts and SSH remotes at `git@git.pushin.eu`.

### Where does the token come from?

`@agntn/credentials/pushin` checks these sources in order:

1. An explicit `{ token }`.
2. `PUSHIN_TOKEN`.
3. The instance login saved by `pun`, the Pushin CLI.

Run `pun login` to save a login. It goes into `pun/hosts.json` under the XDG config directory. `PUN_CONFIG_DIR` changes that location.

Create a personal access token in Pushin.eu Settings, under Security, Personal access tokens. Pushin.eu wants two factor auth on first. forges sends the token as a Bearer token.

Pass `{ token: "" }` to read public repositories anonymously. `users.authenticated` needs a token.

## What it reads

Endpoints are relative to `/api/v1`. In the table, `…` means `/repos/:owner/:repo`.

| Resource       | Endpoint                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------- |
| Repositories   | `GET …`                                                                                         |
| Issues         | `GET …/issues`, `GET …/issues/:number`, `GET …/issues/:number/comments`                         |
| Pull requests  | `GET …/pulls`, `GET …/pulls/:number`                                                            |
| Review threads | `GET …/pulls/:number/comments`, resolved with `PATCH …/pulls/comments/:id`                      |
| Releases       | `GET …/releases`, `GET …/releases/tags/:tag`                                                    |
| Writes         | `POST …/issues`, `POST …/pulls`, `POST …/releases`, `POST …/pulls/:number/comments/:id/replies` |

## What comes back

- Review threads come from the pull request's inline comments. Replies join the thread they answer. A thread is resolved when its root comment is resolved, and a range keeps its first line as `startLine`.
- A merged pull request keeps its `mergeCommitSha`, which the upstream adapter leaves in the raw payload.
- The upstream adapter collects threads from submitted reviews only. Pushin.eu leaves standalone inline comments out of every review. Reading reviews alone would lose them, a bad deal for a code review.
- Replying, resolving and unresolving need a token. Resolving also needs moderator rights.
- More than 2000 inline comments produces a 413, not a partial thread list.
- Issue and pull request events contain comments only.
- An author imported from another forge has a login but no account ID.
- Review verdicts are web UI only. The API can't create or submit a review.
- The inline comment shape is tested against Pushin.eu's OpenAPI schema. No public pull request had inline comments when this provider was written.
- Repository, issue, comment and release reads were checked live on `pjullrich/pushin`, the tracker for Pushin.eu itself.

## Gotchas

### Why do commits and files return 501 on a Git forge?

Because Pushin.eu's REST API has no route for them. No commit log, no contents, trees, tags, branches or comparisons. forges returns 501 before making a request.

Without a token, the 501 also suggests passing one. A token doesn't add the missing routes. Nice try though.

Pushin.eu silently caps `perPage` at 100. Anonymous reads share a rate limit, and anonymous live calls saw `x-ratelimit-limit: 90` per window.

The explorer at `forges.agntn.dev` doesn't run Pushin.eu.

## What isn't there

These operations return 501 with a sentence instead of pretending.

**Pushin.eu has no route for:**

- `commits.*`, `repos.readContents`, `repos.listTree` and `repos.listTags`.
- `pullRequests.listFiles` and `pullRequests.merge`.
- Issue edits. An issue can be read and created, never closed through the API.
- Code search, issue search and pull request search.
- Reactions, issue fields, sub issues and contribution templates.

**Pushin.eu has the route, forges doesn't use it yet:**

- `ciRuns.*`, `pullRequests.listChecks`, `commits.listChecks` and `pullRequests.listReviews`.
- `users.get`, `repos.list` for an organization and pull request edits.
- Posting a new issue or pull request comment.

## Where it lives

`PushinProvider` lives in `src/providers/pushin.ts`. Import it from `@agntn/forges/pushin`.

It uses the upstream `forges/pushin` adapter and `@agntn/credentials/pushin`. Upstream forges marks its Pushin adapter experimental.
