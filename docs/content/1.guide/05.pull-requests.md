## Calls

```ts
const open = await forge.pullRequests.list("owner", "repo", { state: "open" });
const pr = await forge.pullRequests.get("owner", "repo", 1234);
const found = await forge.pullRequests.search("owner", "repo", "renovate");
const files = await forge.pullRequests.listFiles("owner", "repo", 1234, { perPage: 100 });
const checks = await forge.pullRequests.listChecks("owner", "repo", 1234);
const reviews = await forge.pullRequests.listReviews("owner", "repo", 1234);
const comments = await forge.pullRequests.listComments("owner", "repo", 1234);

const created = await forge.pullRequests.create("owner", "repo", {
  title: "docs: fix the deploy link",
  body: "Closes #42.",
  sourceBranch: "fix/deploy-link",
  targetBranch: "main",
  draft: true,
});
```

## The shape

```ts
interface PullRequest extends Issue {
  merged: boolean;
  draft: boolean;
  sourceBranch: string;
  targetBranch: string;
  mergeCommitSha: string;
  mergedAt: string | null; // null until merged
  mergedBy: { login: string } | null;
  headSha: string;
  mergeable: boolean | null; // null while the platform is still computing it
  mergeStatus: string; // the platform's own word
}
```

`mergedBy` needs `get` on GitHub and Gitea: their list responses leave out who merged, so `list` gives the timestamp and `null` for the account. GitLab reports both either way.

A GitLab merge request has an `iid`, that is `number` here. A GitHub pull request is also an issue, so `id`, `labels`, `author` and the dates come from the same place issues get them.

## Search returns less

`search` gives you `PullRequestSearchItem`: the `Issue` fields plus `merged` and `draft`. No branches, no head SHA, no mergeability. GitHub and Gitea search responses simply do not carry them, and fetching them per row would make one search page cost a whole page of requests. Call `get` for the row you actually care about.

## Search across repositories

`searchGlobal` finds an author's PRs without knowing the repositories first. The existing `search(owner, repo, query)` stays scoped to one repository.

```ts
const recent = await forge.pullRequests.searchGlobal("author:octocat created:>=2026-01-01", {
  sort: "created",
  order: "desc",
  perPage: 20,
});
```

Each hit adds `repository` (for example `octocat/Hello-World`) to `PullRequestSearchItem`. Optional `owner` and `repo` narrow the scope; `repo` needs an owner. `sort` accepts `created`, `updated` or `comments`, and `order` accepts `asc` or `desc`. Omit `sort` for GitHub's best match ordering; `order` defaults to `desc`.

Follow `nextPage` while `hasNextPage` is true. `totalCount` is the provider's match count, not the number available to download: GitHub exposes at most `resultLimit: 1000` hits. `incomplete` is true when GitHub marks the response partial, the count exceeds that cap, or rows are dropped because they aren't PRs with a usable repository identity in the requested scope. Narrow the query instead of treating a capped search as a complete history.

`forges_pull_requests_search_global` exposes this contract in MCP (including `forges mcp`), Pi and OMP, without the bodies. GitLab and Gitea return 501; GitHub-compatible hosts without the endpoint do too. This doesn't change their existing repository searches.

## Changed files

`listFiles` turns each changed file into a path, a status and two counts:

```ts
interface PullRequestFile {
  path: string;
  status: "added" | "modified" | "removed" | "renamed" | "copied" | "unknown";
  additions: number | null;
  deletions: number | null;
}
```

No patches. GitLab withholds counts for a collapsed or oversized diff, and those come back as `null`. Never as zero, zero would be a lie.

## Checks

`listChecks` accepts a positive integer `page` and an integer `perPage` from 1 to 100, defaulting to 1 and 30. Invalid values, including a page range beyond JavaScript's safe integers, reject with a `ForgesError` (status 400) before any HTTP request. A bad page isn't an empty set of checks.

`listChecks` reads whatever the platform pins to the head revision: GitHub commit statuses and then check runs of the head SHA, GitLab merge request pipelines for the current head, Gitea commit statuses. Each one is a `PullRequestCheck` with a name, a lifecycle `status` and a terminal `conclusion`, the same two enums [CI runs](/guide/commits) use.

A GitLab project with merged results pipelines or merge trains runs the merge request on a merge commit it builds, so that pipeline carries the SHA of the merge commit, not of the head. It is listed anyway, as the `head_pipeline` of the merge request. GitLab moves that pointer only once a pipeline for a new head exists, so right after a push the previous head's pipeline can still be listed, and earlier pipelines on the same merge ref never are: the API does not say which head they were built from.

A GitLab check is named after its pipeline, the `workflow:name` of `.gitlab-ci.yml`, so a project that never set one lists every check as `pipeline`. The merge request pipeline rows don't carry that name, so each pipeline on the page is read once more, from the project it ran in: for a merge request from a fork that's the fork. Five of those reads go out at a time.

The GitHub statuses matter because branch protection can require them. A CLA bot, Jenkins or Buildkite reports through the Status API, not as a check run, so a page of green check runs isn't a green pull request. The statuses come first, since there are few of them and a page of check runs can be long. `totalCount` counts both, and a status with no target page has an empty `url`. GitBucket has the status route and no check runs. A 404 there, on a host that isn't GitHub or Enterprise, is an empty list, so the statuses still come back. On GitHub that same 404 stays not found.

## Reviews

`listReviews` is who said what about the pull request as a whole: the approvals, the changes requested, the review comments that took no side.

```ts
interface PullRequestReview {
  id: string;
  state: "approved" | "changes_requested" | "commented" | "dismissed" | "pending";
  body: string;
  author: { login: string };
  revision: string; // the commit reviewed, empty when the platform keeps none
  submittedAt: string; // empty when the platform keeps no time
  url: string;
}
```

A request for review that nobody has answered isn't a review and stays out. GitHub and Gitea have real review objects, and a Gitea review dismissed later keeps its verdict in the API, so the dismissed flag wins here. GitLab has none: an approval is a row on the approvals endpoint with its time, a reviewer's stance is a state on the reviewers endpoint without one, and the two merge per user, so `id` there is the user's id. A reviewer who withdrew an approval reads as `dismissed`, a review started and not sent as `pending`. GitBucket has no reviews route at all and says so with an unsupported error. Compare `revision` with `headSha` to see whether a verdict predates the current push. The inline comments a review carries live under [threads](/guide/threads).

`getReview(owner, repo, number, reviewId)` reads one complete GitHub or Gitea review, including its body and verdict. Use the `id` from `listReviews`, not an inline comment id. GitLab has no individual review bodies, so this read returns a 501 rather than treating a user id as a review.

Agent lists keep bodies short. Follow `forges_pull_requests_reviews` with `forges_pull_requests_reviews_get` when a finding falls beyond that excerpt. Nothing is cut from the single-review response.

```ts
const review = await forge.pullRequests.getReview("owner", "repo", 1234, "5678");
console.log(review.body);
```

## Comments

`listComments` on a pull request is the discussion, not the review threads. On GitHub and Gitea it is the same endpoint as issue comments. Inline review comments live under [threads](/guide/threads).
