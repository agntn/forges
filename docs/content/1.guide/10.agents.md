## 68 tools, five surfaces

Every tool is written once, in `src/tools.ts`. [`@agntn/tools`](https://tools.agntn.dev) hands that one definition to the MCP server, both extensions, the `forges` CLI and the AI SDK. Same schema, same description, same error text. Fix it once, fixed everywhere.

Two shortcuts, because models kept tripping over the long form. `platform` defaults to `github`. And `repo` takes the slug everyone writes anyway, `{ "repo": "agntn/keys" }`. An `owner` next to it may repeat the slug's owner. Naming someone else fails. No guessing which one you meant.

Cloudflare Artifacts? Git without the forge around it. So only the five Git reads take `platform: "artifacts"`, and the rest don't even list it. The [Artifacts page](/platforms/artifacts) has the details.

## Several issues, pull requests or threads in one call

Three issues used to mean the same tool three times in a row, like a broken record. Need several at once? Pass a list. One bad id doesn't sink the other nine.

`forges_issues_get` and `forges_pull_requests_get` take a number or a list of up to 10. `forges_threads_get`, `forges_threads_resolve` and `forges_threads_unresolve` take a thread id or a list. Lists are for MCP, Pi, OMP and the AI SDK. The CLI keeps `--number 391` and `--thread-id` to one item per command.

```json
{ "repo": "agntn/forges", "number": 398, "threadId": ["PRRT_a", "PRRT_b", "PRRT_c"] }
```

One value keeps the old answer. A list comes back in the same order. Each item has its key and a `result` or an `error`. Successful resolves stay resolved, so retry only the failed ids. An empty list or one above 10 is refused before any request.

Reads run in parallel. Resolves run one thread at a time, as GitHub asks of mutations. In a local run, three separate calls took about 1.5 s. One list took about 0.5 s, with nearly the same answer size.

Bodies share the single call's 200 000-character ceiling. Ten issues get 20 000 characters each by default. A bigger `maxChars` than that share? Refused. Continuations with `offset` and `bodyHash` take one number.

## Checks that finish

Is CI green yet? Ask `forges_pull_requests_checks` again and again, and it says "still running" again and again. Pass `waitSeconds` instead, up to 300. The call comes back once every check concludes, or when the budget runs out. A timeout isn't an error. You still get the page, plus a `wait` field with what's left.

Every page of checks counts. A green first page with page two still building isn't done.

Right after a push there's a catch. For a moment the pull request can still point at the old head, and that head's checks are all done. Green, settled and wrong. So pass the SHA you just pushed as `headSha`. Until the pull request catches up, you get no rows, a `staleHead` naming the commit it still shows, and the wait keeps going.

`forges_commits_checks` lists checks for a SHA, branch or tag. Like `forges_pull_requests_checks`, it accepts `waitSeconds` up to 300. The shell loop calling `gh api` every 20 seconds can finally go. Some checks arrive after the merge party: a Workers Builds deploy, a release, a publish. They run on the merge commit, outside the pull request's checks.

A branch or tag is pinned to its commit when the call starts, so a push in the meantime doesn't move it. The result's `sha` names that commit, and `wait` matches the pull request version. An empty list never settles it, though. A commit can't say when it was pushed, so a deploy that starts late still gets caught.

## Review bots that edit in place

Green CI, and the bot? A review bot rarely says "done" out loud. Codex edits one sticky comment: `Running` when its round starts, `Completed` when it ends. PR Lens does the same under its own marker.

So `forges_pull_requests_comments` waits too. `marker` keeps the comments whose body has that text. `since` keeps the ones created or edited after it. Both read every page in one call, so there's no cursor.

```json
{
  "repo": "agntn/forges",
  "number": 339,
  "marker": "codex-pull-request-review-summary",
  "since": "2026-10-26T20:50:00Z",
  "waitSeconds": 110
}
```

With `since` at your push, the first edit after it settles the call. Usually that's `Running`. Call again without `since`, and it waits for the next edit after the call starts. That one says `Completed`. Two calls, not 85 lines of `gh` in a shell loop.

You get only the changed comments. Plus `wait`: `settled`, `waitedMs`, `polls`. Bodies are still cut in a list. PR Lens puts its verdict at the bottom, so read that one whole with `forges_pull_requests_comments_get`.

`forges_pull_requests_reactions` plays by the same rules. `author` stands in for `marker`. Its wait also settles when a reaction from the first read goes away. Codex's `eyes` does that when a round ends with findings. You'll find it in `wait.removed`.

A quiet bot isn't an error. The budget runs out, `settled` is `false` and the list is empty. The note says to call again.

Changed your mind halfway? Hit Esc in Pi or OMP, or cancel the call from your MCP client. The wait ends right there. The next poll never goes out. No more five minutes of forges refreshing CI for an agent that's long gone.

Every other read lets go just as fast. A silent host can't hold your session for 30 seconds. The request runs out in the background. Nobody reads the reply.

## Local Git

Two tools read a checkout instead of a forge. No token, no fetch, no writes.

`forges_local_inspect` gives status, tracked files and the last few commit messages in one call. Point `paths` at `*AGENTS.md` and it finds every instruction file. A big repository comes back in pages.

`forges_local_merge_verify` asks something narrower. Is the merge commit on the target? Did these paths land exactly as they were on the PR head? Fetch the target first, then pass the head, the merge commit and the paths.

A match isn't a license to clean up, though. Paths you didn't list weren't checked, and refs move. Look at the live PR before deleting anything. The library has both as `inspectLocal` and `verifyLocalMerge` in `@agntn/forges/local`.

## MCP

```bash
forges mcp
claude mcp add forges --scope user -- npx -y @agntn/forges mcp
```

Or in a client's config:

```json
{
  "mcpServers": {
    "forges": { "command": "npx", "args": ["-y", "@agntn/forges", "mcp"] }
  }
}
```

That's stdio. A host with its own transport takes `createMcpServer()` from `@agntn/forges/mcp`.

Issue and pull request lists leave bodies out and name the tool that reads one in full. A page of busy issues with every body inside would push the conversation that asked for it out of the window. Two small calls beat one huge one.

Searches also leave bodies out unless `bodyChars` asks for the start of each one. Reading the starts of someone's last eight PR bodies takes one search call, not a small pilgrimage through eight more. Comments, reviews and threads keep their bodies, cut to twelve lines and 4,000 characters each, so a heavily reviewed PR wants a small `perPage`.

## Reads, writes and whose account

Reads go through the usual [token chain](/guide/auth). Nothing found? They go out anonymous. That anonymous provider never gets reused for a write, not even by accident. Artifacts has no guest mode, so no token there means a clear error.

Twenty tools write to the host, and their MCP annotations say so. Run a create or a reply twice and you get two of them. Updates, comment edits and deletes, and the merge are marked destructive. Pi asks before each comment edit or delete, which is worth the interruption. A merge doesn't come back, and neither does a deleted comment.

Esc doesn't cut a write short, though. The forge may already have it. So forges waits for the answer. Guessing is how a model posts the same comment twice.

Before a model writes anything, `forges_users_authenticated` tells you whose account it'll use. Two GitHub logins in `gh`? A write can pick one with `account`. forges then asks `/user` whose token that really is and refuses on a mismatch. That check is the point. A `GH_TOKEN` in the environment still wins the lookup, and a reply signed by the wrong person looks exactly like a success. GitLab, Gitea and Artifacts don't take `account`.

The credential stays pinned until `forges_auth_reload` swaps it. Even an expired one. So a rejected token comes back with where it came from and which login to redo. Then the reload. A bare 401 tells a model nothing.

## Hosts stay local

A self hosted forge comes from `FORGES_GITHUB_BASE_URL`, `FORGES_GITLAB_BASE_URL`, `FORGES_GITEA_BASE_URL`, `FORGES_BITBUCKET_BASE_URL`, `FORGES_GITEE_BASE_URL`, `FORGES_AZURE_DEVOPS_BASE_URL`, `FORGES_GITCAFE_BASE_URL` or `FORGES_PUSHIN_BASE_URL` in the agent's environment. `FORGES_ARTIFACTS_BASE_URL` does the same for the Cloudflare API. Never a tool argument, so a model can't aim a call somewhere else. Errors name the status and, on a rate limit, when to retry. Never the endpoint.

A failed call is a sentence for the model. The session survives.

## Pi and OMP

```bash
pi install npm:@agntn/forges
```

Both extensions draw calls and results in the terminal. A repository row, pull requests with their states, a thread with its comments. Pi stops before six writes: creating, editing or merging a pull request, editing an issue, creating or editing a release. It shows what goes out and waits for a yes. No UI to ask? No write. OMP puts its own approval in front of every write.

Which repo is this, anyway? Both extensions answer before the agent asks. Each run gets the checkout's forge remotes in its system prompt, origin and upstream first, with the `platform`, `owner` and `repo` the tools take.

Plain local Git, about 7 ms, no network, no token. Credentials in a remote URL stay out. Without it the model said `unknown`. With it, GitHub, agntn, forges.

## AI SDK

One import gives your model all 68 tools, no wrappers to write.

```bash
pnpm add @agntn/forges ai @ai-sdk/anthropic
```

```ts
import { anthropic } from "@ai-sdk/anthropic";
import { forgesAiTools } from "@agntn/forges/ai";
import { generateText, isStepCount } from "ai";

const { text } = await generateText({
  model: anthropic("claude-sonnet-5-5"),
  tools: forgesAiTools,
  stopWhen: isStepCount(5),
  prompt: "What's still open on agntn/forges?",
});
```

Reads run without asking. The twenty host writes stop at a tool approval request. So does `forges_auth_reload`, which swaps the pinned credential. Why ask? A bare `generateText` loop has nobody there to approve a merge. The model's finger can hover, but it can't press.

Your loop, your call. A `toolApproval` you pass wins over that default:

```ts
await generateText({
  model: anthropic("claude-sonnet-5-5"),
  tools: forgesAiTools,
  toolApproval: { forges_issues_comments_create: "approved" },
  prompt: "Say thanks on agntn/forges#346.",
});
```

It also takes `"denied"`, `"user-approval"` or a function. Keys are the MCP names, and the model reads the same text an MCP client gets. `ai` is an optional peer, any 7.x.

## What comes back

Normalized objects, not prose. Want to check a model's summary against the source? The [Explorer](/explorer) shows the same objects for any public repository.

::caution
Issue bodies, comments and review threads come from whoever has an account. Data to report, not instructions to follow. An agent that reads `ignore previous instructions` in an issue has learned something about the issue. Nothing about what to do next.
::
